# ScienceChess Lab

_by Vladislav Dmitrovsky_

Локальный тренажёр моторики и скорости для ultrabullet. Работает целиком в браузере,
без сервера, аккаунтов и внешних запросов. Все данные лежат в IndexedDB на устройстве.

С Lichess во время игры тренажёр не взаимодействует и вводить ходы за вас не умеет.

## Адрес сайта

Тренажёр опубликован на GitHub Pages. Перед входом — экран доступа с общим
кодом (см. «Доступ» ниже), дальше открывается всем, у кого есть код:

```
https://6c79fv6sdh-wq.github.io/Speed-lab/
```

Сайт обновляется сам. Workflow `.github/workflows/pages.yml` на каждый push
в `main` прогоняет тесты, собирает проект и перезаписывает ветку `gh-pages`,
которую раздаёт Pages. Если тесты падают, публикации не будет.

Запустить публикацию вручную: вкладка **Actions** →
**Сборка сайта в ветку gh-pages** → **Run workflow**.

Настройка Pages уже сделана: источник — ветка `gh-pages`, папка `/(root)`.

## Публикация в /lab/ основного сайта

Отдельно от GitHub Pages этого репозитория готовая сборка может уезжать в
папку `lab/` репозитория `6c79fv6sdh-wq/vladchess-site` (основной сайт
ScienceChess), откуда её раздаёт Pages того репозитория по адресу
`/lab/`. Исходники не смешиваются — только статика после `npm run build`.
Схема и разовая настройка — `docs/lab-integration-brief.md`.

- Работает `.github/workflows/deploy.yml`: по релизному тегу `v*` или
  вручную (**Actions** → **Публикация в vladchess-site /lab/** →
  **Run workflow**) собирает проект и пушит `dist/` в `vladchess-site/lab/`.
- Base path и роутинг уже совместимы с публикацией из подпапки без
  дополнительных настроек: `base: './'` в `vite.config.ts` — все пути к
  ассетам относительные, а вкладки переключаются через `location.hash`
  (`#premove` и т.п.), не через путь — поэтому один и тот же билд одинаково
  работает и в корне (`Speed-lab`), и под `/lab/`. Проверено сборкой,
  выложенной в подпапку и открытой оттуда, — все запросы отвечают 200.
- Нужен секрет `VLADCHESS_SITE_TOKEN` (fine-grained PAT с правом
  Contents: Read and write на `vladchess-site`) — единственный шаг,
  который нельзя сделать автоматически, токен создаётся вручную в
  интерфейсе GitHub. Секрет кладётся в тот репозиторий, откуда реально
  запускается `deploy.yml` (сейчас — `Speed-lab`, см. ниже).
- Публиковать релиз: **Actions → Публикация в vladchess-site /lab/ → Run
  workflow** (кнопкой, без тега) — либо `git tag vX.Y.Z && git push --tags`
  из своего git-клиента. Из среды ассистента пуш тега в `Speed-lab`
  заблокирован политикой этой сессии (обычные пуши в ветки проходят, пуш
  тега — нет, даже лёгкого), поэтому первый релиз опубликован через ручной
  запуск workflow, не через тег. Это ограничение именно ассистентской
  сессии, не репозитория: тег с вашего компьютера или кнопкой в интерфейсе
  GitHub пройдёт нормально.

## Доступ

Без кода приложение вообще не грузится: `boot()` (монтирование вкладок,
чтение IndexedDB) не вызывается, пока код не введён и не подтверждён.
Вместо вкладок посетитель видит публичную витрину (`src/gate.ts`,
рендерится прямо в `#view`): hero с названием и описанием, свайповая
галерея из шести карточек — реальные скриншоты модулей
(`public/showcase/*.webp`, сняты с живого приложения, ничего не
нарисовано вручную), блок «Прогресс» и два действия — «Обсудить занятия»
(основное, ведёт на контакт) и «Уже есть код? Войти» (открывает
`<dialog>` с полем кода). Не логин, не бэкенд — просто фильтр случайных
посетителей и полноценная демонстрация продукта тем, у кого доступа ещё
нет.

Пока показана витрина, `#app` получает класс `app-public`: своя шапка
приложения и пустая полоса вкладок скрыты, чтобы название не дублировалось
в двух местах, а над витриной не висела чужая разделительная линия.
Класс снимается при верном коде.

Три метрики в блоке «Прогресс» (`DEMO_METRICS` в `src/gate.ts`) —
**демонстрационные**: показывают, что именно Lab измеряет, а не чьи-то
настоящие результаты, и прямо подписаны как пример. Выдавать выдуманные
числа за реальные замеры нельзя, поэтому подпись убирать не надо.

- Ссылка кнопки «Обсудить занятия» — в `src/core/access.ts`:
  `CONTACT_TELEGRAM_URL` (используется по умолчанию) и `CONTACT_WHATSAPP_URL`
  про запас. Чтобы вести на WhatsApp вместо Telegram, поменяй, на что
  ссылается `contactLink` в `src/gate.ts`.
- После верного кода устройство запоминает доступ в localStorage
  (`sciencechess-lab-access`) и не спрашивает код повторно, пока токен не
  истёк, — сразу видит вкладки, а не витрину.
- Галерея — нативный `overflow-x: auto` + `scroll-snap-type: x mandatory`
  (свайп на телефоне и трекпаде работает сам, без JS и без библиотек),
  плюс свои стрелки/точки поверх. Чтобы добавить/заменить скриншот —
  положить `.webp` в `public/showcase/` и дополнить массив `SLIDES`
  в `src/gate.ts`.

### Проверка кода — на сервере, не в бандле

Раньше код доступа лежал прямо в JS константой (`ACCESS_CODE`) — кто угодно
мог открыть devtools, прочитать его в собранном бандле и войти без спроса,
а «доступ» в localStorage можно было проставить себе вручную, вообще не
зная кода. Теперь код знает только сервер.

**Архитектура**: фронтенд (GitHub Pages, как и раньше) + один Cloudflare
Worker (бесплатный тариф). Никакого Firebase/Supabase/аккаунтов — только
воркер и штатная для него KV-хранилище (тоже бесплатный тариф, с запасом
для этой нагрузки).

1. `src/gate.ts` при вводе кода шлёт его POST-запросом на воркер
   (`POST /login { code }`) по HTTPS.
2. Воркер сравнивает код с секретом `ACCESS_CODE` (хранится только как
   Cloudflare Secret, в репозитории и в бандле его нет). Верно — выдаёт
   токен, подписанный приватным ключом ECDSA P-256 (тоже секрет), со
   сроком годности `TOKEN_TTL_SECONDS` (по умолчанию 30 дней). Неверно —
   401. Слишком много неверных попыток подряд — 429 с нарастающей паузой
   (см. «Rate limiting» ниже).
3. Фронтенд сохраняет токен в localStorage и на каждом заходе проверяет
   его подпись и срок сам — офлайн, публичным ключом (`crypto.subtle.verify`
   в `src/core/access.ts`). Публичный ключ — не секрет: им можно только
   проверить чужую подпись, подделать токен нельзя. Поэтому вернувшийся
   ученик с валидным токеном не спрашивает сеть на каждом заходе, и
   приложение по-прежнему открывается офлайн, как и раньше — сеть нужна
   только один раз, при самом вводе кода.
4. Токен истёк — `hasAccess()` вернёт `false`, снова покажется витрина
   с полем кода.

**Rate limiting**: воркер считает неудачные попытки по IP в KV
(`RATE_LIMIT_KV`). После 5 подряд — пауза 60 секунд; если продолжают
пытаться и после паузы — следующая пауза вдвое длиннее, и так до потолка
в час. Успешный вход обнуляет счётчик. Пока пауза активна, воркер даже не
сравнивает присланный код (значит, и правильный код в это время не
пройдёт) — перебрать код нормально невозможно.

**CORS**: воркер принимает POST на `/login` только с источников из
`ALLOWED_ORIGINS` (`worker/wrangler.toml`) — и проверяет `Origin`
не только в CORS-заголовках ответа (это соблюдает лишь браузер), но и
на сервере, отказывая явно (403) прямым запросам с чужого/пустого
`Origin`. Оба текущих адреса Lab — под одним и тем же origin
`https://6c79fv6sdh-wq.github.io` (GitHub Pages одного владельца, разные
пути одного домена), поэтому значения по умолчанию хватает на оба сразу.
Появится свой домен — впиши через запятую и `wrangler deploy` (без
пересборки фронтенда).

> ⚠️ **Порядок важен.** Пока воркер не задеплоен, а `WORKER_URL`/
> `PUBLIC_KEY_JWK` во фронтенде пустые, вход не работает вообще —
> `login()` сразу отвечает «Вход временно недоступен» — а старые токены
> (если сайт уже был опубликован раньше) больше не проходят проверку. Это
> ожидаемо: код и раньше было небезопасно хранить в бандле. Но чтобы
> сайт не остался без входа даже на время, сначала до конца пройди шаги
> ниже (воркер живой, оба значения вписаны), и только потом собирай и
> публикуй фронтенд с этими изменениями.

**Первоначальный деплой воркера** (один раз с твоей машины —
из среды ассистента `wrangler` пушить некуда, доступа к твоему аккаунту
Cloudflare у него нет):

```bash
cd worker
npm install
npx wrangler login                              # один раз, откроет браузер
npx wrangler kv namespace create RATE_LIMIT_KV   # выведет настоящий id —
                                                  # впиши его в wrangler.toml
                                                  # вместо REPLACE_WITH_KV_NAMESPACE_ID
node tools/generate-key.mjs                      # выведет пару ключей —
                                                  # ЗАПУСКАЙ САМ, не проси
                                                  # ассистента, приватный
                                                  # ключ не должен попасть
                                                  # в чат или куда-либо ещё
npx wrangler secret put ACCESS_CODE              # вставь код доступа, когда попросит
npx wrangler secret put SIGNING_PRIVATE_KEY_JWK  # вставь приватный ключ из вывода generate-key.mjs
npx wrangler deploy                              # выведет адрес *.workers.dev
```

Дальше вручную, один раз:

- В `src/core/access.ts` впиши адрес воркера в `WORKER_URL` и публичный
  ключ (из вывода `generate-key.mjs`) в `PUBLIC_KEY_JWK`.
- Пересобери и опубликуй фронтенд как обычно (`npm run build`, обычный
  push в `main` или релиз — см. выше). Сборка GitHub Actions воркера не
  касается вообще: это отдельный деплой, руками, не в CI.

#### То же самое, но без терминала (с телефона/планшета)

Все шаги выше делает `wrangler` из консоли. Тот же результат можно
получить целиком в браузере, через Cloudflare Dashboard — ничего не
устанавливая:

1. **Аккаунт.** dash.cloudflare.com → регистрация (бесплатно, карта не
   нужна).
2. **Ключи.** Открой «Кузницу ключей» — небольшую страницу, которая
   работает целиком в браузере и ничего никуда не отправляет
   (`worker/tools/generate-key.mjs` делает то же самое, но из терминала;
   это её веб-версия) → «Сгенерировать пару ключей» → скопируй оба
   значения в заметки. Приватный ключ — секрет, публичный — нет.
3. **Воркер.** В Dashboard: Workers & Pages → Create → Create Worker →
   любое имя (например `sciencechess-lab-gate`) → Deploy (сразу с
   заготовкой — её заменим). Дальше Edit code (Quick Edit) → стереть всё
   → вставить целиком содержимое [`worker/dashboard-paste.js`](./worker/dashboard-paste.js)
   → Save and deploy.
4. **KV-хранилище.** Workers & Pages → KV → Create namespace → имя любое
   (например `rate-limit`) → Create. Вернись в воркер → Settings →
   Bindings → Add binding → KV Namespace → variable name **строго**
   `RATE_LIMIT_KV` → выбрать созданный namespace → Save.
5. **Обычные переменные.** Там же, Settings → Variables and Secrets →
   Add → тип Text (не Encrypt):
   - `ALLOWED_ORIGINS` = `https://6c79fv6sdh-wq.github.io`
   - `TOKEN_TTL_SECONDS` = `2592000`
6. **Секреты.** Там же, Add → тип **Encrypt**:
   - `ACCESS_CODE` = сам код доступа, который будешь давать ученикам
   - `SIGNING_PRIVATE_KEY_JWK` = приватный ключ из шага 2 (весь JSON
     целиком, одной строкой)

   Save and deploy.
7. **Адрес воркера.** На странице воркера справа/сверху виден адрес вида
   `https://sciencechess-lab-gate.<твой-поддомен>.workers.dev` (если
   спросит — включить `*.workers.dev` subdomain, это тоже кнопка в
   интерфейсе). Скопируй его.
8. Пришли мне **только** этот адрес и публичный ключ из шага 2 (это два
   не-секретных значения) — остальное (правки `src/core/access.ts`,
   сборку и публикацию фронтенда) сделаю сам, без доступа к твоему
   аккаунту Cloudflare мне это не нужно.

Приватный ключ и код доступа при этом способе так же не попадают ни в
репозиторий, ни в чат — только в шаги 2 и 6 внутри твоего браузера и
Dashboard.

**Сменить код доступа позже** — не трогая фронтенд и ключи:

```bash
cd worker && npx wrangler secret put ACCESS_CODE
```

Старые токены, выданные до смены, останутся действовать до истечения
своего срока (воркер не хранит список выданных токенов — они
самодостаточны за счёт подписи). Если нужно разлогинить всех немедленно —
сгенерируй новую пару ключей (`generate-key.mjs`), обнови секрет
`SIGNING_PRIVATE_KEY_JWK` и `PUBLIC_KEY_JWK` во фронтенде: старые токены
подписаны старым ключом и перестанут проходить проверку.

**Секретов в этом репозитории нет и быть не должно**: `ACCESS_CODE` и
`SIGNING_PRIVATE_KEY_JWK` — только `wrangler secret put`, `worker/.dev.vars`
(локальный аналог для `wrangler dev`) в `.gitignore`. `PUBLIC_KEY_JWK` во
фронтенде — не секрет, это ожидаемо публичная половина пары.

## Телефон и размер доски

Доска подстраивается под экран. `boardSize` в калибровке — это **желаемый**
размер: его выбирают на большом экране, он хранится в настройках и
переносится между устройствами. Фактический размер считает `fitBoardSize()`
(`src/core/settings.ts`) — минимум из желаемого, доступной ширины и
доступной высоты, округлённый вниз до кратного 8, чтобы клетка была целым
числом пикселей.

- Доступную ширину `Board` меряет по родителю контейнера (`.board-area`),
  а не по самому контейнеру: `.board-host` — inline-block и ужимается по
  доске, то есть о свободном месте не знает.
- Высота считается от окна минус `BOARD_HEIGHT_RESERVE` (запас под липкую
  полосу вкладок). Именно от окна, а не от блока страницы: высота блока
  сама зависит от высоты доски, вышла бы обратная связь.
- Высоту окна берём зондом с `height: 100svh`, а не через
  `clientHeight`. На iOS `clientHeight` меняется, когда адресная строка
  сворачивается при прокрутке, — доска пересчитывалась бы прямо посреди
  упражнения. `svh` — это высота при развёрнутой адресной строке, она
  постоянна и меняется только от поворота экрана.
- Пересчёт идёт на `ResizeObserver` плюс `resize`/`orientationchange`,
  после смены размера обязателен `api.redrawAll()` — иначе Chessground
  оставит фигуры разложенными по старой сетке и клики поедут.
- Выходит: 390×664 — доска 352 px (упирается в ширину), 844×390 в
  альбомной — 312 px (упирается в высоту), 320 px — 280 px, планшет и
  десктоп — прежние 480 px. На узком экране размер уходит ниже
  `BOARD_SIZE_MIN`: лучше вся доска целиком, чем 320 px с обрезанной
  вертикалью h.
- В замеры пишется **фактический** размер (`measuredCalibration()` в
  `src/core/session.ts`). Иначе разбивка «по размеру доски» на вкладке
  «Прогресс» складывала бы замеры с монитора и с телефона в одну строку.
- В «Настройках» под ползунком видно, что доска ужата и до
  скольки.

Прокрутка страницы пальцем по доске намеренно заблокирована
(`blockTouchScroll`, `touch-action: none`): иначе перетаскивание фигуры
уезжало бы в прокрутку. Листать страницу на телефоне надо мимо доски —
так же ведёт себя доска на Lichess.

## Движок

В «Цейтноте» соперника считает Stockfish 18 Lite, однопоточная WASM-сборка.
Однопоточная выбрана намеренно: многопоточной нужен SharedArrayBuffer,
а для него — заголовки COOP/COEP, которых на GitHub Pages не выставить.

Файлы лежат в `public/engine` и в предзагрузку service worker не попадают:
иначе первое открытие сайта весило бы 7 МБ. Движок подтягивается при первом
использовании и после этого работает офлайн.

Сила задаётся через `UCI_Elo` (диапазон сборки 1320–3190), то есть «Эло 2200»
означает именно это значение, а не название профиля. Отдельно выбирается темп
хода — он влияет только на задержку перед ответом.

Рядом остаётся простой бот на один полуход: он не требует загрузки и полезен,
когда нужен заведомо слабый и мгновенный соперник.

Проверка того, что шкала силы работает:

```bash
npm i --no-save stockfish
MT=50 G=12 node tools/engine-match.mjs
```

Замеренный результат: Эло 2200 против Эло 1400 — 88% очков (10,5 из 12),
Эло 2200 против Эло 3000 — 0% (0 из 12). Шкала монотонна и реально влияет
на игру. Абсолютная привязка `UCI_Elo` к рейтингу Lichess — заявление
разработчиков Stockfish, независимо я её не проверял.

Stockfish распространяется по GPLv3, текст лицензии — `public/engine/LICENSE-stockfish.txt`.

## Оформление доски

В настройках выбирается тема доски и набор фигур. Цвета полей и подсветок —
переменные CSS на `:root` (см. `src/board/theme.ts`), поэтому смена темы
применяется сразу ко всем доскам, включая уже открытую.

Наборы фигур лежат в `public/piece/<набор>` и в предзагрузку service worker не
попадают: наборов несколько, а пользуются одним. Выбранный набор кешируется
при первом показе и дальше работает офлайн.

## Где лежат данные упражнений

| Что | Файл |
| --- | --- |
| Линии дебютных репертуаров, SAN | `src/data/repertoire.ts` |
| Позиции для модуля Premove, FEN (рукописные) | `src/data/premove-positions.ts` |
| Позиции «Форсированное взятие», импортированные | `src/data/premove-forced-imported.ts` |
| Исходный JSON этих позиций | `data/lichess-safe-premove-200-white.json` |
| Задачи «висящая фигура» | `src/data/puzzles-hanging.ts` |
| Исходный PGN этих задач | `data/lichess-hanging-piece-200-white.pgn` |
| Задачи «мат в один ход» | `src/data/puzzles-mate.ts` |
| Исходный PGN этих задач | `data/lichess-mate-in-1-320-white.pgn` |

Задачи импортируются скриптами:

```bash
node tools/import-puzzles.mjs data/lichess-hanging-piece-200-white.pgn > src/data/puzzles-hanging.ts
node tools/import-mate-puzzles.mjs data/lichess-mate-in-1-320-white.pgn > src/data/puzzles-mate.ts
node tools/import-premove-forced.mjs data/lichess-safe-premove-200-white.json > src/data/premove-forced-imported.ts
```

Каждый скрипт проверяет задачи движком правил и отбрасывает битые: для
«висящей фигуры» — что ход легален и это взятие, для «мата в один ход» —
что ход легален и после него на доске мат, для позиций «Форсированное
взятие» — что FEN валиден, ожидаемый ход соперника легален и является
взятием, а ответный ход пользователя легален после него и бьёт на то же
поле. FEN/SAN/UCI везде пересчитываются самим скриптом, а не копируются
из источника. Импортированные позиции подмешиваются к рукописным в
`positionsOf('forced-capture')` — остальные режимы Premove не затрагиваются.
Чтобы добавить свои задачи, положи файл рядом и прогони нужный скрипт на нём.

Все файлы проверяются автотестами: `tests/repertoire.test.ts` проигрывает каждую
линию движком от начальной позиции, `tests/premove-positions.test.ts` и
`tests/premove-forced-imported.test.ts` проверяют валидность каждого FEN и
легальность ожидаемого, ответного и неожиданного ходов. Если добавишь линию
или позицию с ошибкой, `npm test` это поймает.

Загрузка своего PGN в первой версии не предусмотрена.

## Вкладки

Порядок навигации повторяет путь ученика: что делать сегодня → сама
тренировка → накопленный прогресс. Новых тренировочных режимов при этом
не добавлялось — связаны в систему уже существующие.

1. **Сегодня** — назначенная на день короткая тренировка из трёх шагов и
   одна кнопка «Начать тренировку». Состав дня даёт `today-plan.ts`
   (разминка и реакция каждый день, третий шаг чередуется), см. ниже.
2. **Моторика** — 30 повторов source-target с телеметрией указателя.
3. **Premove** — форсированное взятие (в т.ч. 200 реальных задач Lichess),
   safe/unsafe, отмена.
4. **Реакция** — бесплатное взятие (200 реальных задач Lichess), мат в один ход
   (320 задач Lichess), безопасный шах, дельта позиции; экспозиция без лимита /
   500 / 300 / 200 мс — работает во всех четырёх упражнениях.
5. **Дебюты** — три репертуара, задержка ответа на каждом узле, заминки.
6. **Цейтнот** — партии 15/10/5 секунд против Stockfish с выбором силы
   либо против простого бота.
7. **Прогресс** — сводные таблицы, экспорт и импорт JSON, очистка измерений.
   Раньше вкладка называлась «Данные»; id остался `data`, чтобы старые
   ссылки вида `#data` продолжали работать.

Отдельно, не в ряду с модулями, — **Настройки** (бывшая «Калибровка»):
размер доски, способ ввода, координаты, профиль устройства, метка
настроек указателя. Это настройка, а не тренировка, поэтому в основной
навигации её нет. При первом запуске на устройстве (когда калибровку ещё
ни разу не сохраняли — `hasSavedCalibration()`) тот же экран
показывается как короткая первоначальная настройка с кнопкой «Готово,
к тренировке», после чего открывается «Сегодня».

### Как устроено «Сегодня»

- Состав дня считает `src/modules/today-plan.ts` — модуль без DOM и без
  базы: на вход дата и сессии, на выход план с отметками. Поэтому
  поведение проверяется тестами (`tests/today-plan.test.ts`).
- План на конкретный день постоянен: он назначен, а не выпадает заново
  при каждом заходе. Третий шаг чередуется по номеру дня, так что три дня
  подряд не повторяются.
- Отдельного хранилища галочек нет. Шаг засчитан, только если сегодняшняя
  сессия модуля доведена до **полноценного** конца — `sessionIsComplete()`
  в today-plan.ts: моторика — ровно 30 повторов, premove/реакция — вся
  очередь заданий сессии (8/10), дебюты — все 4 линии, цейтнот — партия
  доиграна, а не сдана досрочно. «Прервать» и уход с вкладки тоже
  вызывают `session.finish()` (иначе замер потерялся бы), поэтому просто
  «сессия есть» недостаточно — отметка о выполнении и есть измерение, но
  измерение обязано быть полным.
- Пороги дублируют константы модулей (`REPS`, `TASKS_PER_SESSION`,
  `LINES_PER_SESSION`) — не импортом (это дало бы цикл: те же модули
  импортируют `stepAfter()` для кнопки «Следующее упражнение», см. ниже),
  а сверкой в тестах через реальные экспортированные значения.
- «Итог дня» — более мягкий счётчик, использует `sessionCountsToday()`
  (сессия сегодня и доведена до какого-то конца, не обязательно полного):
  сколько всего заданий сделано и сколько суммарно времени потрачено
  (`endedAt − startedAt` по сессиям), плюс отдельно `X / 3` пройденных
  модулей строгим критерием выше. Прерванная попытка не даёт галочки, но
  время и число заданий по ней всё равно видны — тренировка не «исчезает».
- После каждого шага, начатого из «Сегодня» (кнопки «Начать тренировку»,
  «Перейти», «Повторить»), внутри самого модуля после завершения сессии
  появляется кнопка «Следующее упражнение: <модуль> →» и сразу открывает
  следующий шаг плана (`stepAfter()` — чисто по порядку дня, не по
  отметкам: даже прерванная попытка предлагает идти дальше, а вернуться к
  пропущенному можно с «Сегодня»). После последнего шага — авто-возврат
  на «Сегодня». Флаг «пришёл из плана» — одноразовый, в `sessionStorage`
  (`markPlanNavigation`/`consumePlanNavigation` в `core/session.ts`):
  открыл модуль напрямую через меню — кнопки не будет, стандартная
  самостоятельная тренировка не меняется.

## Хранение, экспорт и импорт

Всё лежит в IndexedDB `sciencechess-hyperlab`: настройки калибровки, сессии,
замеры и статистика дебютных узлов.

На вкладке **Прогресс**:

- **Экспорт в поле** — JSON в текстовое поле,
- **Скачать файл** — тот же JSON файлом,
- **Импорт из поля** и **Импорт из файла** — обратная загрузка (слияние по id),
- **Очистить измерения** — удаляет сессии, замеры и статистику узлов,
  настройки калибровки при этом остаются.

Синхронизации между устройствами нет и не планируется: перенос только через экспорт.
